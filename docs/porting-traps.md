# Porting traps and lessons

Numbered lessons from real bugs found while porting `@dotenvx/dotenvx` v2.24.1. Each says what went wrong, why, and how to avoid it. Referenced from [AGENTS.md](../AGENTS.md) by trap number (`#NN`); keep numbers stable and append new traps at the end. Numbers 1-16 are the parity-suite traps; the rest continue in one sequence.

## Pin history (why the pin sits where it does)

The submodule was once pinned 3 commits past the `v2.24.1` tag (`c55d3981`); corrected 2026-10-02. The default flip to OS-native secret stores (Keychain/Credential Manager/Secret Service), which this port does not implement, lands in those 3 commits (`ade777bc`/`e0d9f38a`/`c55d3981`, "store to os secret store by default"), immediately after the tag. Confirmed empirically: the real `v2.24.1` tag with no flags and non-interactive stdin already writes a plain `.env.keys` file, matching this port. The `--no-native --no-armor` ParityTest workarounds are therefore harmless but unnecessary at this pin and are kept on purpose: the next bump will likely land past the flip again.

`precommit`/`prebuild` are current at the pin but deprecated on upstream HEAD in favor of `dotenvx protect` (a command that does not exist at the pin); `gitignore`/`genexample`/`scan`/`ext` are not deprecated there, only moved to an "Advanced" doc section. A future bump past the introduction of `protect` must check upstream's migration story before assuming a straight port still makes sense.

## Traps (parity suite first, then everything else)

1. **Test only what the *pinned* commit actually supports.** `--file`/`DOTENV_FILE` were forward-ported ahead of the v2.24.1 pin (see the submodule-pin note up top); a parity test comparing against the pinned Node CLI for those flags fails with "unknown option", not because our port is wrong, but because there's nothing to compare against yet. Check `dotenvx/src/cli/dotenvx.js --help` at the current pin before writing a scenario for a flag you learned about from upstream's CHANGELOG.
2. **`keypair`/fresh-key generation is already flaky to test at this pin - but there's a fix for `encrypt`, not for `keypair`.** `src/lib/resolvers/keypair.js` looks up a private key by matching an *already-present* `DOTENV_PUBLIC_KEY` in the `.env` file against a keyring; it does not derive a public key from an arbitrary private key dropped in `.env.keys` with no matching public key yet - there's no flag-based workaround for this, use a fixed, pre-verified encrypted fixture instead (see `FixedKeypairFixture.cs` for the shared constants - generate once via our own `dotnet ... encrypt`, verify both CLIs can independently decrypt it, then hardcode it - every test class needing a deterministic keypair references this one shared file rather than its own copy). Genuine bidirectional live round-trips reusing that existing keypair (one CLI's `set` creates fresh ciphertext this run, the other's `get` decrypts it, then reversed) work fine and aren't flaky - `set`'s "reuse the existing key" path is deterministic on both sides. See `NodeCreatesFreshCiphertextThatDotnetDecrypts`/`DotnetCreatesFreshCiphertextThatNodeDecrypts` for that pattern.
   For `encrypt`'s *fresh key generation* itself (no existing keypair anywhere yet - neither `.env` nor `.env.keys`), by default Node's "no existing key" path routes through the custodian/keyring/native-store resolver and does not even write a `.env.keys` file (confirmed empirically: `ls .env.keys` → not found after a successful `encrypt`), so there's nothing file-based for .NET to read - not just non-determinism, an outright missing artifact. The fix: pass `--no-native --no-armor` to Node's `encrypt`, which forces it back onto plain-file `.env.keys` writing (verified stable across repeated runs; the key *bytes* still differ every run, which is fine and expected - only the *mechanism* needs to be deterministic). `.NET`'s `encrypt` has no native/armor concept at all (out of scope for this port) and always plain-file-generates, so it needs no equivalent flag - passing `--no-native`/`--no-armor` to it is simply "unrecognized argument". See `DotnetGeneratesFreshKeypairThatNodeUses`/`NodeGeneratesFreshKeypairThatDotnetUses` in `EncryptDecryptParityTest.cs` for the pattern - this is the one place in the suite that tests genuine fresh key generation (not reuse) cross-implementation.
   **This flakiness isn't confined to the two tests that deliberately exercise it** (found 2026-09-26, when the suite started intermittently failing 7 UNRELATED tests with "failed to save private key to Windows Credential Manager" or a structurally-wrong `.env`): ANY test that calls `set`/`encrypt` with encryption enabled against a `.env` with no pre-existing `DOTENV_PUBLIC_KEY` hits this exact path as a side effect, even if the test isn't testing key generation at all - a same-directory `.env.keys` file with a private key already in it does NOT help, since `resolvers/keypair.js` looks for the public key in `.env`'s own content first. Fixed by adding `--no-native --no-armor` to every affected test's Node call specifically (never to a `RunBothAsync`'s shared args - confirmed live that .NET errors immediately on either flag, so any test needing this fix must call `RunNodeAsync`/`RunDotnetAsync` separately rather than `RunBothAsync`). When adding a NEW `set`/`encrypt` parity scenario, check whether its setup leaves a `DOTENV_PUBLIC_KEY` in `.env` already (e.g. via `FixedKeypairFixture`/`WriteFixedEncryptedFixture()`) - if not, and the scenario isn't specifically about native/armor behavior, add these flags to its Node call up front rather than waiting for it to start failing intermittently.
3. **`npm`/`npx` etc. resolve to `.cmd` files on Windows.** `Process.Start` with `UseShellExecute = false` won't auto-resolve those the way a shell would; `NodeParityFixture` resolves the actual path via its own PATH/PATHEXT-aware `FindOnPath` and uses that, not the bare command name.
4. **Compare stdout and exit code, not stderr wording**, unless the scenario is specifically about stderr content. This suite found and fixed two real, independent bugs in the CLI's own stream routing: `Console.Out`/`Error` defaulted to `Environment.NewLine` (`\r\n` on Windows; Node always emits `\n` - fixed in `Program.cs`), and `DotenvxCustomLogger` sent every non-Error/Critical level to stdout, when upstream's `src/shared/logger.js` only sends `info` to stdout - `error`, `warn`, **`success`**, `help`, `verbose`, and `debug` all go to stderr, keeping stdout script-safe (fixed via `DotenvxLogEvents`/`EventId`-based routing, since several dotenvx log levels collapse onto the same Microsoft.Extensions.Logging `LogLevel`). (`get`'s missing-key message was once a known stderr-wording gap here too, but a byte-diff re-check on 2026-09-26 found it's since become identical - fixed incidentally by the systemic error-message-printing work, Trap above, without this note being updated at the time; re-verify a "known cosmetic difference" claim like this live before citing it, since it can go stale silently.) `ls`'s "found N .env files..." summary line is on stderr and includes elapsed time, so it's excluded from comparison the same way.
5. **`ls` had zero coverage until 2026-09-19 and immediately turned up two real bugs the moment it was exercised end-to-end** - a reminder that "the code reads right" and "it's actually been run against the reference CLI" are different claims. `Ls.cs`'s `Patterns()` returned `[]` (matching nothing) instead of the documented `.env*` default when no `-f` was given - `ls` with no args silently listed **zero files**. Once fixed, patterns still needed a `**/` prefix (matching upstream's `patternsFor`) to match nested files at all - a bare `.env*` picomatch pattern only matches root-level paths; `Directory.GetFiles` doesn't understand `**/` glob syntax, so `FilePaths()` now enumerates every file once and lets "**/"-prefixed picomatch globs do the actual filtering, mirroring upstream's Fdir-crawl-then-filter shape. Also: the reference file had *moved* from `src/lib/services/ls.js` (doesn't exist at this pin) to `src/lib/resolvers/ls.js` without the port's doc-comment being updated - always re-check where a reference file actually lives at the pin, since the reorg (see submodule-pin note) silently moves things.
6. **Global log-level options (`-l`/`-q`/`-v`/`-d`) silently broke when placed after a subcommand with an optional positional argument.** `dotnet get -v` printed `[MISSING_KEY] missing -v key` and `dotnet ls -v` crashed with `DirectoryNotFoundException` for a directory literally named `-v` - System.CommandLine only recognized `LoggingRootCommand`'s options *before* the subcommand name unless each is marked `Recursive = true` (needed to match commander.js's actual "global option, usable anywhere" behavior). This is a correctness bug independent of any specific subcommand - `GlobalOptionsParityTest.cs` locks it in so it can't silently return for a future subcommand.
7. **`JsonSerializerOptions { WriteIndented = true }` defaults to `Environment.NewLine` (`\r\n` on Windows) for its indentation line breaks** - Node's `JSON.stringify` always emits `\n`. This bug was duplicated three times (`GetAction`'s `--pretty-print`, `KeypairAction`'s `--pretty-print`, `LsAction`'s `--json`) before any parity test exercised those code paths - when you find one instance of a bug pattern, grep the whole `src/Dotenvx/Actions/` tree for the same shape (`JsonSerializerOptions` + `WriteIndented = true`) rather than assuming it's isolated. Fixed by setting `NewLine = "\n"` explicitly (a real property on `JsonSerializerOptions`/`JsonWriterOptions` since .NET 9).
8. **`Picomatch(globs)` with `globs: null` does NOT mean "match everything"** - it means "match nothing" (an empty include list, so `.Exists(...)` is always false). Every existing call site (`Encrypt.cs`'s `_include`/`_exclude`, `GetAction.cs`'s `FilterKeys`) relies on an *external* `keys?.Length > 0` guard before consulting the predicate when the option wasn't actually passed - don't call `Picomatch(possiblyNullArray)` and trust its return value directly without that guard, or "no filter given" silently becomes "filter out everything."
9. **Don't byte-for-byte diff a flag whose output includes the whole process environment** (e.g. `get --all`). `node` and `dotnet` each inject their own incidental env vars into a spawned child process, so `RunBothAsync` + a full `StandardOutput` comparison will intermittently disagree for reasons that have nothing to do with the port. Instead, pass a distinctive marker variable through the `env` parameter and assert only that it round-trips identically (see `GetParityTest.AllFlagIncludesMachineEnvVarsIdentically`).
10. **`set`'s missing-file default is `""` (empty string), NOT `encrypt`'s sample kit (`HELLO="World"`)** - both substitute *something* for a missing file by default (both disabled by the same `--no-create` flag, both fixed the same way in their respective services), but `set KEY value` is about to insert its own pair immediately, so starting from `""` is correct per `dotenvx/src/lib/transforms/set.js`; copying `Encrypt.cs`'s `SampleEnvKit` constant into `Sets.cs` would be wrong. Check the specific transform file for each command rather than assuming a bug fix's shape transfers unchanged to a sibling command with a superficially similar name.
11. **A "no existing constructor" NSubstitute failure (`ArgumentException: Can not instantiate proxy of class`) after adding a parameter to a service class's constructor means you missed a call site** - specifically, `Substitute.For<T>(ctorArgs...)` calls (which need an exact arity match for Castle's proxy generator; C#'s default-parameter sugar doesn't apply to reflection-based construction) are a *separate* set of call sites from that same class's own `Factory` static field reassignments (`T.Factory = (a, b, c) => mock;`), even though both exist for the same reason (mocking) and often live in the same test file. Grep for both `Substitute.For<ClassName>(` and `ClassName.Factory =` separately when a constructor signature changes - fixing only one leaves the other broken at test-run time, not compile time, in `Dotenvx.Core.Test`'s `MainTest.cs` specifically (it constructs mocks both ways for the same class).
12. **`decrypt --mask` only affects `--stdout` output** - unlike `get --mask` (which affects all output paths), `decrypt.js`'s `options.mask` is read *only* inside the `if (options.stdout)` branch; it never touches what actually gets written to disk on a normal (non-stdout) decrypt. Confirmed by reading the full file, not just the `--help` text. Also masks *every* parsed key blindly (including `DOTENV_PUBLIC_KEY` itself) - there's no special-casing of "sensitive" vs "structural" keys in `maskEnvSrc.js`, so the port (`MaskEnvSrc` in `Helpers/MaskEnvSrc.cs`) shouldn't add any either.
13. **`decrypt.js`'s per-key decryption failures don't abort the rest of the file, and `error`/`changed` are independent, not mutually exclusive.** One malformed/undecryptable value in a file with other, valid encrypted values still lets those other values decrypt and get written - `[DECRYPTION_FAILED]`/etc. gets logged AND the file still gets its "decrypted" success line, same run. This port's `Decrypt.cs` originally called the per-key decrypt helper with no try/catch inside its loop (one bad key aborted the whole file), and `DecryptAction.cs` used `else if (processedEnv.Changed)` after the error check (silently dropping the partial output whenever any key failed). Also: `decrypt`'s per-key error message is *always* the generic `[DECRYPTION_FAILED] could not decrypt {key}` regardless of the actual cause (missing key, wrong key, malformed data) - confirmed by calling `@dotenvx/primitives`' `parsearrays()` directly (from within the submodule dir) with all three causes and getting the identical generic message every time. This is a real, `decrypt`-command-specific coarsening, different from `run`/`get`/`set` (which use primitives' singular `parse()` and DO surface the specific `WRONG_PRIVATE_KEY`/`MISSING_PRIVATE_KEY` cause) - don't "fix" `decrypt`'s messages toward matching `run`/`get`'s specificity, and don't assume a single primitives entry point's error-shape generalizes to every other entry point.
14. **A CLI action's single-KEY branch can silently ignore `--format` entirely.** `KeyPairAction.cs`'s `if (key != null)` branch printed only the bare value no matter what `--format` was, when `keypair.js` specifically special-cases `options.format === 'colon' && key` to print `${key}:${value}`. Found by an opencode delegation writing the missing test and correctly declining to "fix" it blind - always check whether a format/flag that's handled in the "all results" branch is *also* supposed to apply to the "single result" branch before assuming they're independent code paths.
15. **`System.CommandLine` 2.0.0's `Option<T[]?>` resolves to a non-null EMPTY array when a multi-value flag is omitted, never `null`** - confirmed via a scratch console-app probe against the actual installed package. Any `parseResult.GetValue(someArrayOption) ?? someDefault` idiom silently never applies its fallback - check `.Length > 0` explicitly instead. Found while adding `gitignore`'s `--pattern` option (a bare `dotenvx gitignore` created nothing at all before the fix, since the `.gitignore` file's own `touchFile && Patterns.Length > 0` guard also failed against the empty array). **Audited 2026-09-24: no other current action is actually affected.** Every other `string[]?`-typed option either defaults to an empty array anyway (`GetAction`/`RunAction`'s `--ignore`, order-invariant to this bug) or resolves its non-empty default at the *service* layer via a proper `is { Length: > 0 }` check rather than `??` on the raw `GetValue()` result (`Ls.Patterns()`'s `.env*` default, which is why `ls` with no args always worked correctly). `gitignore` was unusual in resolving its default directly in the action layer instead of delegating to the service - that's what exposed the bug. Still worth checking this specific shape (`GetValue(arrayOption) ?? nonEmptyDefault` at the action layer) if a new action needs one.
16. **A JS error's custom `.help` override set AFTER its factory already computed `.messageWithHelp` is dead code** - `errors.js`'s factories set `e.messageWithHelp` as a plain, already-computed string property (not a getter), so any later `error.help = "custom text"` reassignment (e.g. `genexample.js`'s "? add it with [echo ...]" override on a `missingEnvFile()` error) never actually surfaces - `catchAndLog`'s `messageWithHelp || message` always sees the stale generic version. Confirmed live (`dotenvx genexample -f .env.nonexistent` prints the generic `fix:` URL, never the custom text), not just from reading source - a JS test file itself can be written from source-reading alone without live verification and encode the "intended" behavior rather than the real one. When a JS action sets `.help` after calling an `errors.js` factory, verify live whether it actually changes anything before porting it as real behavior.
17. **`System.CommandLine` 2.0.0's `Command.Hidden` cannot be used to hide a command from one parent's `--help` listing while still letting that command's own `--help` render normally** - it's a single flag on the `Command` object, and `HelpBuilder.Write` does `if (context.Command.Hidden) return;` before rendering anything, so a permanently-`Hidden` command produces completely empty `--help` output for itself too (confirmed empirically building the `ext` command group, 2026-09-23 - `dotenvx ext --help` silently returned nothing). There is no public `HelpBuilder` customization API in the actual shipped 2.0.0 package (it's an internal type, `HelpAction` has no `Builder` property - GitHub's `main` branch source doesn't match what's actually in the NuGet package; verify via a scratch console app + reflection against the real installed DLL, not by reading upstream System.CommandLine source directly, if this comes up again). The fix for "hide from root's listing only": wrap the root's `HelpOption.Action` (a `SynchronousCommandLineAction`) to toggle the child's `Hidden` to `true` only for the single `Invoke()` call where `parseResult.CommandResult.Command` is the root itself, restoring it in a `finally` - see `DotenvxRootCommand.FilteringHelpAction`.
18. **A service's own constructor default and its CLI action's default for the same conceptual option can silently diverge** - `prebuild.js`'s `Prebuild` class defaults `directory` to `'./'` in its own constructor, but `prebuild.js`'s CLI action's commander argument defaults to `'.'` - two different literal strings for "current directory," both valid, but a helper that only special-cases an exact `"."` match (not `"./"` too) passes CLI-level live comparisons fine (which only ever exercise the action's own default) while silently breaking for any DIRECT unit test that constructs the service with no arguments. When porting a service with its own default parameter value, write at least one test that actually uses the bare, no-args constructor - don't rely solely on CLI-level comparisons that route through the action's own (possibly different) default.
19. **`precommit.js`'s git-staged-file check silently fails for nested files on Windows, and this port faithfully reproduces it rather than "fixing" it** - `path.join(directory, file)` normalizes to the platform separator (backslash on Windows), but `git diff --name-only -z` always emits forward-slash paths regardless of OS, so the two never match for a nested path there; the file gets silently treated as "not staged" and skipped from enforcement entirely. Confirmed live: staging an unencrypted nested `.env` file and running the real Node CLI on Windows exits 0 with no error. Don't "fix" this cross-platform quirk toward what seems more correct - it's upstream's own real, live-confirmed behavior.
20. **`@dotenvx/primitives`' `sealed()` requires EVERY occurrence of a duplicate key to be encrypted, not just the last** - and neither `DotenvParse`'s default (last-value-wins) nor its own `collectAllValues` parameter (despite the name, keeps only the FIRST occurrence via `TryAdd`) can express this; `Sealed.cs` needed fully dedicated parsing. Don't assume an existing "collect all values"-sounding parameter actually does that without reading its implementation.
21. **`src/Dotenvx/Dotenvx.csproj` (the CLI project) has no `InternalsVisibleTo` entries at all** - only `Dotenvx.Core.csproj` grants that, to `Dotenvx.Test`/`Dotenvx.Core.Test`/`Dotenvx.Configuration.Test`. A test-only swappable seam for CLI-only logic with no natural `Dotenvx.Core` service backing it (e.g. `scan`'s external-process capture, which has no service class) can't live in `src/Dotenvx/Actions/` as an `internal` member - it needs to go in `Dotenvx.Core`'s `Helpers` regardless of whether the logic conceptually "belongs" to a single CLI action, following the `Fsx.cs`/`GitHelper.cs` delegate-swap convention. Check this constraint before assuming a plan's "keep it inline in the action" suggestion for a new testable seam will actually compile against `Dotenvx.Test`.
22. **`run`/`get`/`validate` all shared the identical missing-capability gap, and fixing it exposed a second real bug in an unrelated existing helper.** Upstream's `run.js`/`get.js`/`validate.js` all resolve their env-item list via `buildCommandEnvs.js` + `resolveDirectoryFilepath.js`, which lets a bare directory (not just a file) be passed to `-f`/positional args - `-f ./config` resolves to `./config/.env` (or, with `--convention`, to each convention file joined under that directory). This port's `RunAction.cs`/`GetAction.cs`/`ValidateAction.cs` all used an older, simpler pattern (`Conventions(convention)` unconditionally prepended, explicit items appended, no directory resolution at all) - found missing in `run`/`validate` on 2026-09-24, and confirmed `get` had the byte-for-byte identical gap the moment the fix was scoped (same upstream helper call, `buildCommandEnvs(normalizeDotenvConfigPath(this.envs), options.convention)`) - fixed all three together rather than leaving one sitting unfixed right next to the others. Ported as new `Helpers/BuildCommandEnvs.cs` + `Helpers/ResolveDirectoryFilepath.cs` (plus a new `Fsx.IsDirectorySync` delegate-swap static). `ValidateAction.cs` deliberately does NOT wrap its explicit items in `NormalizeDotenvConfigPath` first, matching `validate.js`'s own call (`buildCommandEnvs(this.envs, options.convention)`, no normalize) - a genuine, confirmed asymmetry with `run`/`get` (validate doesn't fall back to `DOTENV_FILE`/`DOTENV_PATH`/`DOTENV_F` when no `-f`/`--env` given), preserved rather than "fixed" toward consistency. Live-verifying this against Node then turned up a SECOND bug: `NodePathJoin.cs` (from the earlier `ext prebuild`/`precommit` work) only collapsed a directory argument that was *exactly* `"."`/`"./"`, because `prebuild`/`precommit` never pass anything more complex - but Node's `path.join` does full lexical segment normalization (`path.join('./config', '.env')` → `config\.env`, `path.join('a/../..', 'x')` → `..\x`), and a user-supplied `-f ./config` routinely has exactly the embedded `./` the old check didn't handle. Rewrote `NodePathJoin` to do real segment-based normalization (drop `.`/empty segments, resolve `..` against a stack, preserve a drive-letter/absolute root) - re-ran the full suite afterward to confirm every existing `Prebuild`/`Precommit` test (which only ever exercises the simple cases) still passed unchanged, confirming it was a pure capability addition. **Lesson**: when one action turns out to have a missing-capability gap relative to a shared upstream helper, grep every OTHER action calling that same helper before considering the fix done - and re-verify any existing "good enough for its one caller" helper you now depend on more heavily, live, against the actual new input shapes it wasn't originally exercised with.
23. **A helper that computes a fallback value once and reuses it in two branches needs the SAME fallback in both branches - porting it separately per-branch is an easy way to silently diverge.** `envResolution/determine.js`'s `determine()` computes `defaults` once up front (the `.env` file, or, if any `DOTENV_PRIVATE_KEY`/`DOTENV_PRIVATE_KEY_<env>` is set, the guessed private-key-specific filename(s) instead) and reuses that SAME value in both its "no envs at all" branch and its "envs given but none is a file" branch. `DetermineEnvs.cs` computed the private-key-aware default correctly for the first branch but hardcoded the plain `.env` default in the second - so `dotenvx run --env "FOO=bar"` (no `-f`) with `DOTENV_PRIVATE_KEY_PRODUCTION` set silently loaded `.env` instead of `.env.production`. Found by inspection while working on an unrelated fix (`buildCommandEnvs`), not because any test caught it - no upstream OR ported test exercised this specific combination before. Fixed by computing `defaults` once and reusing it in both branches, matching the JS shape exactly, plus a new `DetermineEnvsTest.cs` (no prior test file existed for this helper at all).
24. **"Verified byte-for-byte identical" is only true if you actually diffed bytes - eyeballing rendered terminal text past ANSI codes is not the same claim, and this session got it wrong twice before catching it.** Colored/prefixed output (error/warn/verbose/debug/success) was pervasively broken across the ENTIRE CLI - `GetColorDepth.cs` was missing upstream `colorDepth.js`'s very first line (`if (stream && !stream.isTTY) return 1`), so .NET's output never degraded to plain text even when piped/redirected, and `error`/`warn`/`verbose`/`debug` were ALSO missing their symbol prefixes entirely ("☠ "/"⚠ "/"┆ ") since upstream's `logger.js` formatter functions add these themselves rather than each call site including them. Found only because a NEW `scan` parity test (which, unlike the rest of the parity suite, needed to diff stderr content on purpose) failed - not because any of this session's many manual "compare the live output" checks caught it, even though several of those checks pasted both outputs side by side and declared them identical. Also found in the same sweep: `Success` used color "green" instead of upstream's real "amber"; `Info` was missing its "gray" coloring; `SuccessV` was an entirely fabricated concept (real `logger.js` has one `success` function, not a distinct version-tagged variant) whose two callers were building `"[dotenvx@version] injecting env (N)..."` when upstream emits `"⟐ injected env (N)..."` - wrong tense, fictional version prefix, missing symbol, all at once, in the single most common success message the CLI prints. **Lesson: when a live-verification claim matters, actually pipe both outputs to a file and `xxd`-diff them (per this file's own "Verifying against the real Node CLI" section) - don't trust a side-by-side terminal read, especially for anything involving color codes, which visually "look right" far more easily than they byte-match.**
25. **A full systematic stdout+stderr sweep across every command found 4 more real bugs the exact same day the logging fix landed - the pattern generalizes further than any single fix.** `set`/`encrypt`/`decrypt`'s success/no-change messages were wrong across the board (wrong symbols, wrong pluralization, and two entirely FABRICATED "key added to .env.keys"/"next run..." hint lines in `set`/`encrypt` with zero basis in any visible upstream version - not deprecated, never existed). `keypair` on a missing `.env` file returned exit 0 with null keys instead of Node's raw ENOENT error + exit 1, AND had no try/catch around its resolver call at all (a second bug on top). `run`/`get`/`validate`/`Main.Config()`/`Main.Get()` could surface specific `WRONG_PRIVATE_KEY`/`MISSING_PRIVATE_KEY` codes that the real Node CLI can NEVER produce for these commands - confirmed live that `@dotenvx/primitives`' `parse()` (what the shared `resolvers/envs.js` all these commands route through actually calls) always coarsens every decrypt failure to generic `DECRYPTION_FAILED`; those specific codes are real only for `main.js`'s differently-named-but-similar standalone `parse()` FUNCTION, which manually loops per-key with its own `decryptKeyValue()` call instead of going through the resolver. `ls` never printed its `▣ found N .env files...` summary line AT ALL (a fully missing feature, not a timing-cosmetic gap - it's a raw `console.error()` call bypassing the logger entirely). **Lesson: when a "cosmetic" logging bug turns out to be pervasive, don't assume it's isolated to what you already found - a scripted sweep across every command (redacting non-deterministic content) is worth the upfront cost, and this session's own bug count proves it: five real message-text/behavior bugs found in one sweep, none caught by ~800 existing unit tests, because the parity suite deliberately never diffs stderr and unit tests only check what someone already thought to assert.**
26. **A shared internal helper class can have TWO legitimate callers needing OPPOSITE error-handling behavior for the same "missing input" condition - the fix belongs in the caller that needs it, not the shared class.** `Services.KeyPair` is used both by the `keypair` CLI command (which upstream deliberately crashes on a missing `.env` file) AND internally by `FindPrivateKey.cs`/`FindPublicKey.cs` as an "does a key already exist yet" lookup for `run`/`encrypt`/`set`'s fresh-key-generation logic (which needs a graceful null return for files that legitimately don't exist yet, e.g. `encrypt` creating a brand-new sample kit). Adding a missing-file existence check inside `KeyPair.cs` itself broke `encrypt`/`Main.Config()` on a fresh file - confirmed via a full-suite regression across unrelated test classes (`ConfigTest`, `EncryptTest`, a `ParityTest` scenario) that had nothing to do with `keypair` on the surface. Moved the check to `KeyPairAction.cs` (the CLI-specific consumer) instead. **Lesson: before adding validation/error-throwing to a shared helper, grep every caller first - "this class is only used by the command with the same name" is an assumption worth verifying, not a given.**

Live-verified byte-identical against Node, including confirming neither side leaks a literal BOM character into the decoded key name. **Lesson: `DetectEncoding.cs` and `ReadFileX`'s encoding switch are two independently-maintained pieces of the same feature (one PRODUCES an encoding-name string, the other CONSUMES it) - adding or changing a detected encoding name in one without checking the other's switch cases is exactly the kind of two-sided drift this bug is** (whoever ported `DetectEncoding.cs` correctly copied Node's exact string constant, but `ReadFileX`'s consuming switch was written against a *different*, .NET-idiomatic assumption of what that string would be).

41. **`Fsx.ReadFileX` now preserves a leading BOM through a read-modify-write round-trip, matching Node - but the first attempt broke plain parsing of any BOM-prefixed file, and needed a second, cross-cutting fix before it was safe.** Found while checking whether `set`/`decrypt`/etc. preserve a UTF-16LE or UTF-8 source file's leading BOM after a rewrite: confirmed live that Node DOES (`ef bb bf` UTF-8 BOM bytes reappear in the rewritten file even when the source was UTF-16LE), while this port's `Fsx.ReadFileX` (using `File.ReadAllText(path, enc)`) silently dropped it, because that overload's `StreamReader` auto-detects and strips a leading BOM matching the requested encoding. Root cause: Node's raw `Buffer`/`fs.readFileSync` decode never strips a BOM at all - it survives as a literal U+FEFF character in the decoded string (`Encoding.GetString(bytes)` in .NET behaves the same way, unlike `File.ReadAllText`).
   Switching `ReadFileX` to decode via `enc.GetString(ReadFileSync(path))` (matching Node's raw-decode behavior) fixed write-back preservation - but broke plain reading of any BOM-prefixed file outright: `dotenvx get HELLO` on a BOM-prefixed file started returning `[MISSING_KEY]`, because `DotenvParseRegex` (and every other regex in this port mirroring an upstream `\s`-based JS pattern) uses .NET's `\s`, which does **not** match U+FEFF - confirmed directly (`node -e "console.log(/\s/.test('\uFEFF'))"` → `true`; .NET's `char.IsWhiteSpace('\uFEFF')` → `false`). JavaScript's `\s` metacharacter explicitly includes U+FEFF per the ECMA-262 spec; .NET's does not. Node's parser therefore silently tolerates a leading BOM before the first key (the `\s*` before the key group eats it); this port's ported regexes didn't.
   **Fixed properly the next day** by adding `\uFEFF` as an accepted alternative alongside the leading `\s*`/`(\s*)?` in every regex in this port mirroring that upstream shape: `DotenvParse.cs`'s `DotenvParseRegex`, `Parse.cs`'s `LineRegex` (the one `run`/`get`/`set`/`encrypt`/`decrypt` actually route through via `Main.cs`'s standalone `Parse()`), `ValidateEnvExample.cs`'s `ScanLineRegex`, `Del.cs`'s `RemoveKey` line regex, and `Append.cs`/`Replace.cs`'s inline key-matching regexes (the latter two CAPTURE the leading-whitespace group and re-emit it in the replacement, so widening it to `[\s\uFEFF]*`/`([\s\uFEFF]*)?` also correctly preserves a leading BOM there, not just skips it). Only the FIRST `\s*`/`(\s*)?` immediately after the line-start anchor in each pattern needed widening - a BOM only ever occurs at byte offset 0, never mid-line - the rest of each pattern's `\s` usages were left untouched. With that in place, `ReadFileX` was switched back to the raw-byte decode. Live-verified byte-identical against Node for `get` (read), `set` (write-back preservation), and `del` (removing the first key correctly drops the BOM along with it), for both UTF-8 and UTF-16LE BOMs.
   **Lesson: verify a "matches Node's raw decode behavior" fix against BOTH ends of the behavior it touches (write-back preservation AND ordinary parsing) before considering it done** - the first attempt's failure didn't show up until deliberately testing a plain `get` on the exact fixture the fix was meant to serve, not just the write-back path that motivated it; a cross-language regex-metacharacter difference (`\s` semantics) was the actual root cause, not anything specific to file I/O. Also surfaced while fixing this: `DelTest.cs`'s constructor blanket-mocks `Fsx.ReadFileSync = _ => []` for every test in the class, and its `TestRunMissingEnvFile` only ever passed because `ReadFileX`'s old implementation never actually consulted that delegate - a coincidental decoupling between two static seams that PASSED, not a verified-correct test. Fixed regardless (now explicitly overrides `Fsx.ReadFileSync` to throw `FileNotFoundException` for that one test) since the old version was accidentally correct rather than deliberately correct.

42. **`--version`/`-V` only worked before the subcommand name, same bug class as trap #6's log-level options.** `dotenvx get --version` fell through to `get`'s `[KEY]` positional argument instead of printing the version, exiting 1 with `[MISSING_KEY] missing key (--version)` where Node's commander (which treats `--version` as recursively available, same as `-l`/`-q`/`-v`/`-d`) prints the version and exits 0. `System.CommandLine`'s built-in `VersionOption` is only added to the root command and isn't recursive by default - fixed the same way as trap #6, setting `Recursive = true` on it inside `DotenvxRootCommand.UpdateBuiltInCommands` (the same method that already touches `VersionOption` to add the `-V` alias). Live-verified `get --version`/`run --version`/`-V` all now work identically at both the root and subcommand level.
    **The separate version-STRING question this trap originally left open (this port printed `1.0.0+<git-hash>` against Node's `2.24.1`) was resolved 2026-10-02** by the versioning-lockstep policy established the same day (see the submodule-pin note at the top of this file): `Dotenvx.csproj`'s `Version` now tracks the exact pinned tag. `GlobalOptionsParityTest.VersionFlagAfterSubcommandIsRecognizedOnBothSides` and the new `RootVersionFlagMatchesExactly` both now compare the version string byte-for-byte (confirmed live: both CLIs print exactly `2.24.1`), tightened from the original "just exit 0" assertion once the policy made an exact-match claim honest.

43. **.NET's default `\w` regex metacharacter is Unicode-aware; JS's `\w` is ASCII-only - so a non-ASCII key name (e.g. `HÉLLO=World`) was silently accepted as a valid key by this port's parser, while Node's real parser rejects the whole line entirely (`{}`, not even a partial match).** Found via a sweep testing unicode key names. Confirmed directly: `Regex.IsMatch("É", @"\w")` → `true` in .NET's default mode, `false` under JS semantics. Fixed by adding `RegexOptions.ECMAScript` (a built-in .NET mode that makes `\w`/`\d`/`\s` ASCII-only, matching JS's real character-class semantics) to every regex in this port using `[\w.-]+` for key matching: `DotenvParse.cs`'s `DotenvParseRegex`, `Parse.cs`'s `LineRegex`, `ValidateEnvExample.cs`'s `ScanLineRegex`, `Replace.cs`'s `GetQuotes()` regex. `Del.cs`'s `RemoveKey`/`Append.cs`/`Replace.cs`'s OTHER regexes don't need it - they match a specific, already-known key via `Regex.Escape(key)`, never an arbitrary `[\w.-]+` character class. `RegexOptions.ECMAScript` is compatible with `RegexOptions.Multiline` (already used by all four) but NOT with most other option combinations - confirmed via a scratch probe that it does NOT also make `\s` match U+FEFF the way JS's `\s` does (that's a separate, JS-spec-specific quirk unrelated to ECMAScript-mode compatibility - trap #41's explicit `[\s\uFEFF]` union is still needed alongside it, they solve two different cross-language regex divergences). Live-verified byte-identical against Node, including confirming the BOM-tolerance fix and this ASCII-`\w` fix work correctly together in the same pattern.
   **Tooling note surfaced while fixing this**: writing the literal 6-character text `\uFEFF` (backslash-u-F-E-F-F) via the Edit/Write tools silently converts it into the actual U+FEFF character on disk, regardless of context (comments, string literals, regex patterns) - confirmed this happens even for a fresh, isolated, single-line file write, so it isn't a verbatim-string or C#-parsing artifact, it's the tool layer itself. This corrupted every comment and verbatim-string regex pattern from trap #41's original fix (the ACTUAL escaped C# string literals using `\\uFEFF`, e.g. `Del.cs`'s inline pattern, were unaffected - only single-backslash `\uFEFF` text was converted). Recovered via `sed` from a Bash shell (which does not have this behavior) rather than the Edit tool. **Lesson: if `\uFEFF` (or likely any `\uXXXX`-shaped escape text) needs to appear as literal TEXT rather than the actual character on disk, write it via Bash (`printf`/`sed`/heredoc), not the Edit/Write tools** - verify with `grep -c $'\xef\xbb\xbf' <file>` (or the equivalent byte sequence for the target codepoint) after any edit that mentions such an escape, since the corruption is invisible in normal tool-result previews and only shows up as a build/behavior failure (or, worse, a silently-wrong-but-compiling regex) later.

## 2026-09-29: parallel static code-audit sweep found 6 real bugs, all missed by live flag-combination testing

After the dynamic (live CLI, flag-combination) sweep hit diminishing returns, ran a STATIC code audit instead: four parallel forked agents each did a line-by-line re-read of a subset of C# action/service files against their pinned-commit JS source, comparing every branch/message/log-level directly rather than testing observable behavior. Found 6 real, previously-undetected bugs in ~800 lines of "already extensively tested" code - none of them showed up in the ~40 rounds of manual flag-combination sweeping earlier in this session, because none of them require an unusual FLAG combination to trigger; they're wrong on the most ordinary possible invocation of each feature. **Lesson generalizes: static code review and dynamic behavioral testing find different bug classes - a codebase that has been heavily flag-fuzzed can still have wrong wiring in code paths nobody happened to combine with the "interesting" flags being tested.**

44. **`decrypt -k SPECIFIC_KEY` (writing to file, no `--stdout`) decrypted and rewrote ALL keys instead of just the one requested - a straight constructor-argument mistake.** `DecryptAction.cs`'s non-stdout branch called `new Decrypt(envItems.ToArray(), null, excludeKey, envKeysFilePath)` - passing `null` where the constructor's second parameter is `keys`. The `--stdout` branch correctly passed `keys` through; only the file-write branch had the bug, which is presumably why this port's own ParityTest suite never caught it - every existing `-k` scenario happened to use `--stdout`. Confirmed live: Node's `decrypt -k HELLO` on a two-key encrypted file left the OTHER key (`FOO`) still encrypted; this port decrypted both. Fixed by passing `keys` instead of `null`.
45. **`run <command>` without a literal `--` separator always failed with "ambiguous command", when real Node supports it via a fallback heuristic - and the two existing unit tests for this exact scenario were themselves misported from the start, asserting the opposite of what the real upstream test does.** `run.js`'s gate is `if (commandArgs.length < 1)` alone; `hasSeparator` only selects which error message to print when that gate fires. Node's own `this.args` (commander's parsing) is typically empty without `--` (since `run` declares no positional argument), triggering `inferCommandArgsFromProcessArgv` - a deliberate fallback that scans raw `process.argv`, skips `-f`/`--env-file` (and its value) and any `-`-prefixed flag, and returns the first plausible non-flag token onward as the command. `RunAction.cs`'s gate was `commandArgs.Length < 1 || !hasSeparator` - the extra `|| !hasSeparator` has no JS equivalent, and rejected a bare `dotenvx run node -e "..."` (no `--`) even though System.CommandLine's own `_args` (a plain `ZeroOrMore` positional) ALREADY naturally captures the trailing command tokens the same way JS's fallback ends up doing, just via a completely different mechanism (no manual argv-rescan needed in C# at all). Fixed by removing the `|| !hasSeparator` from the gate, matching JS exactly - `hasSeparator` still selects the error message, only reached when `commandArgs.Length < 1` is genuinely true.
   The two existing unit tests (`RunActionTest.TestRunEnvFileAmbiguousArgumentsMissingDoubleDash`/`...EnvFileEmpty`) asserted the exact WRONG behavior (exit 1, "ambiguous command" error) for this scenario - confirmed via `git show f1ffd157` era equivalent, i.e. directly reading `dotenvx/tests/cli/actions/run.test.js`'s real `'run - envFile (ambiguous arguments, missing --)'` tests: both stub `args: []` and a `process.argv` matching this exact shape, and assert `envsResolver()` WAS called with verbose/debug/success logging happening normally - SUCCESS, not failure. Whoever ported these two tests apparently inferred the expected behavior from the test NAME alone ("ambiguous arguments") without reading what the test body actually asserts - a live warning for this exact class of mistake. Fixed both tests to mock `Run.Factory`/assert success, matching the real upstream test bodies.
46. **`set KEY` with no value had no `MISSING_VALUE` handling at all - a total feature gap, not a subtle mismatch.** `set.js` checks `value === undefined || value === null`: if stdin isn't a TTY, throws `[MISSING_VALUE] missing value (KEY)` (exit 1); if it IS a TTY, prompts interactively for a hidden password. This port had no code path for either - `_valueArgument` was a required, exactly-one-arity argument, so a missing value failed at System.CommandLine's own parse level with a generic message instead of either of JS's two paths. Fixed the non-TTY path only (a plain, unambiguous bug): `_valueArgument`'s arity is now `ZeroOrOne`, and a `null` value throws a new `MissingValueException` matching JS's exact message/code/help URL. The TTY-interactive-prompt path remains deliberately unimplemented - this port has no interactive-prompt infrastructure anywhere (consistent with the project's general scope), and the realistic scripted/automated usage this port targets almost always hits the non-TTY path anyway.
   Also removed, in the same file: a fabricated `_logger.Debug($"{key} set{withEncryption} to {value} ({envFilePath})")` call with no JS equivalent anywhere in `set.js`'s per-file loop (which only calls `logger.verbose` on the changed branch) - low severity since it's debug-level only, but it logged the plaintext value for an operation whose entire purpose is often secrecy.
47. **`keypair KEY` printed an empty line and exited 1 for a key that WAS derived but has a `null` value (e.g. `DOTENV_PUBLIC_KEY` on a plaintext-only file), when Node prints the literal text `"null"` and exits 0.** `keypair.js`'s single-key branch checks `results === undefined` (the key is entirely ABSENT from the resolved object) - not falsy - so a present-but-`null` value falls through to `console.log(results)`, and JS's template-literal/console.log coercion renders `null` as the string `"null"`. `KeyPairAction.cs` used `Dictionary<string,string?>.GetValueOrDefault(key)`, which returns `null` for BOTH "key absent" and "key present with a null value" - it can't distinguish the two cases the way JS's `undefined`-vs-`null` check can. Fixed by switching to `TryGetValue` (whose `bool` return correctly separates "found" from "value is null") and printing the literal string `"null"` when the key is found but its value is `null`, matching both the plain and `--format colon` output shapes.
48. **`ls` listed `.env*` files inside macOS bundle-extension directories (`.app`/`.key`/`.numbers`/`.pages`/`.photoslibrary`) that real Node's crawler never even visits.** `ls.js`'s Fdir-based crawler has an explicit `DEFAULT_EXCLUDED_DIRECTORY_EXTENSIONS` set and never descends into `node_modules`/`.git` or a directory matching one of those five extensions - files inside aren't candidates for the listing at all, at the crawl level, not the filter level. `Ls.cs`'s `FilePaths()` instead enumerated the WHOLE tree unconditionally via `Directory.GetFiles(_cwd, "*", SearchOption.AllDirectories)`, then filtered via glob patterns that happened to cover `node_modules`/`.git` (both have dedicated `_ignore` globs) but had no equivalent for the bundle extensions at all. Notably, `LsAction.cs`'s own `CountCrawledDirectories` (used only for the summary line's directory count) ALREADY correctly implemented this exact exclusion set - the fix pattern existed in the codebase, just wasn't applied to the actual file-listing method. Fixed by replacing the flat `Directory.GetFiles` call with a manual recursive walk (`Ls.EnumerateFiles`) that prunes excluded directories during the crawl, matching both `ls.js` and `LsAction.cs`'s own established pattern.
49. **`rotate` on a file that errors (missing `.env`/`.env.keys`, etc.) printed a misleading `○ no change (thatfile)` summary line alongside its real warning - something the real historical `rotate.js` never does, because `unchangedFilepaths` is dead code upstream that's never actually populated.** Read the full historical `rotate.js` (`git show f1ffd157:src/lib/services/rotate.js`): `this.unchangedFilepaths` is initialized as an empty `Set()` and never has anything added to it anywhere in the class - `changedFilepaths.add(...)` only runs as the LAST line inside the success path's try block. `Rotate.cs` instead bucketed every non-`Changed` row (including error rows, since `row.Changed` only ever becomes `true` on success) into `_unchangedFilePaths` unconditionally after the try/catch. Confirmed via the real historical test file too (`git show f1ffd157:tests/lib/services/rotate.test.js`'s `'#run (no arguments)'`/`'#run (no env file)'` tests both assert `ct.same(unchangedFilepaths, [])` - empty - for exactly these error scenarios) that this port's OWN two corresponding unit tests had been misported to assert `UnchangedFilePaths.ShouldBe([".env"])` instead - fixed both to assert `ShouldBeEmpty()`, matching the real historical test bodies. Fixed `Rotate.cs` to only bucket into `_changedFilePaths` on success, leaving `_unchangedFilePaths` permanently empty (matching upstream's own dead-but-real behavior exactly, not "improving" it toward something that looks more complete) - `RotateAction.cs`'s `else if (result.UnchangedFilePaths.Length > 0) { logger.Info(...) }` branch is therefore correctly unreachable in practice, same as it is upstream.

50. **`Replace.cs` only ever updated the LAST occurrence of a duplicate key, when `@dotenvx/primitives`' `upsert()` (the live-oracle-confirmed successor to the now-deleted `replace.js` - see the closed-out "not yet fixed" item this replaced) updates EVERY occurrence, each keeping its own quote style.** Found finishing that exact live-oracle investigation: `upsert(e,t,n)` parses `e`, and when the key already exists, walks EVERY occurrence's value (not just the parsed last-value-wins result), swapping each one in via a unique placeholder token before a final pass substitutes the real new value in - explicitly designed to handle files where a key appears more than once. `Replace.cs` instead computed a single last-value-wins `parsed[key]` and built ONE regex matching that specific value's text, so `Regex.Replace`'s default all-matches behavior only ever coincidentally replaced other occurrences sharing the identical stale value - a duplicate key with genuinely different values per occurrence (confirmed live: `FOO=old1` / `FOO=old2`, `dotenvx set FOO new`) left every occurrence except the last one untouched. Fixed by collecting every occurrence's value+quote+position up front (`FindKeyOccurrences`) and splicing each one's own new value in by position, back-to-front so earlier indices stay valid - deliberately left the existing 0-or-1-occurrence code path completely untouched (zero regression risk to the heavily-tested common case) and only forked to the new multi-occurrence path when `FindKeyOccurrences` finds more than one match.
51. **`set`/`encrypt` both ignored the `_PLAIN` key-name exemption entirely, and `Sets.cs` had an extra, upstream-less condition that force-re-encrypted a value that hadn't actually changed.** `set.js`'s `noEncrypt = !options.encrypt || isPlainKey(key)` and `encrypt.js`'s `if (isDotenvPublicKey(key) || isPlainKey(key)) continue` both exempt any key ending in `_PLAIN` from encryption, unconditionally - confirmed live that `encrypt` leaves `HELLO_PLAIN=NotSecret` untouched, and `set HELLO_PLAIN mysecret` (default encryption on) stores it as plaintext, with NO `.env.keys`/public-key side effects either (since `noEncrypt` also gates set.js's own "generate a keypair if none exists yet" branch). Neither `Sets.cs` nor `Encrypt.cs` had any `IsPlainKey` check at all - confirmed via grep that the already-ported `IsPlainKey` helper (added earlier for `run --redact`) was referenced only by `RedactedValues.cs`. Separately, `Sets.cs` had a `goingFromPlainTextToEncrypted = wasPlainText && _encrypt` condition with no upstream basis, forcing `changed = true` (and thus re-encryption) any time an existing plaintext value's key was being set again with encryption on, REGARDLESS of whether the value actually changed - confirmed live (`set FOO bar` on an existing plaintext `FOO=bar`, encryption on) that real Node reports "○ no change" and leaves the value as plaintext; set.js's real comparison is unconditionally `value !== before` alone, nothing else. Fixing this surfaced a stale existing unit test (`SetsTest.TestRunFindsEnvFileWithEncryptAndSettingFromUnencryptedToEncryptedSameValue`) that had been asserting `changed: true` for this exact scenario via an artificial `DOTENV_PUBLIC_KEY` process-env override not present in the real historical JS test it was named after (retrieved via `git show 98f4373a^:tests/lib/services/sets.test.js` - itself pre-dating the `@dotenvx/primitives` refactor) - live-verifying the ACTUAL fixture (`tests/monorepo/apps/unencrypted/.env`) against the current pinned Node CLI confirmed "no change" is the real, current, correct behavior, and the test was rewritten to match.

52. **`Main.cs` (the `Dotenvx.Core`/`Dotenvx.Configuration` library API, entirely separate from the CLI actions) had drifted from fixes already applied to the CLI side earlier this session - a second parallel implementation of the same logic, not touched by those fixes.** Found via a static audit fork covering `Get.cs`/`Run.cs`/`Main.cs` specifically because no CLI action calls into `Main.cs` at all (confirmed via grep - only `Dotenvx.cs`'s public facade and `Dotenvx.Configuration`'s `UseDotenvx()` do). Six confirmed, unrelated-looking bugs traced back to this single root cause:
    - `Config()`/`Get()`/`Parse()`/`Set()` all split `error.message`/`error.help` into two separate logger calls instead of the established single `(error as DotenvxException)?.MessageWithHelp ?? error.Message` pattern (the very first trap in this file, and trap #25 - apparently only ever fixed in `src/Dotenvx/Actions/*.cs`, never here).
    - `Config()` built its env-item list via plain `BuildEnvs(options)` instead of the `buildConfigEnvs`-equivalent pipeline (`BuildCommandEnvs`/`ResolveDirectoryFilepath`, trap #22) real `config()` uses - a directory `Path` entry never resolved to `{directory}/.env}` the way `run`/`get`/`validate`'s CLI actions already correctly do. Ported as `BuildConfigEnvs.cs` (mirrors `buildConfigEnvs.js`'s `{ ...options, convention: undefined }` then `buildCommandEnvs(buildEnvs(...), options.convention)` shape). This surfaced two of this port's OWN `MainTest.cs` tests as stale: they asserted `MISSING_ENV_FILE`/a thrown exception for exactly this directory-argument scenario, matching the OLD pre-`buildConfigEnvs` behavior - confirmed via `dotenvx/tests/lib/main.test.js` that the real test was renamed (dropping "attempt on") and now asserts SUCCESS, while a separate, still-current `get`-specific test with the OLD title/behavior exists precisely because `get()` (unlike `config()`) never routes through `buildCommandEnvs` at all.
    - `Get()` never called `NormalizeDotenvConfigConvention`/`NormalizeDotenvConfigIgnore` (both already implemented and already used by `Config()`) - so `DOTENV_CONVENTION`/`DOTENV_IGNORE` (and their `DOTENV_CONFIG_` variants) were silently respected by `Dotenvx.Config()` but ignored by `Dotenvx.Get()`, with no upstream basis for the asymmetry.

Added `ConfigOptions.Mask` (shared, since real `config()` masks too) and ported `maskProcessedEnvs.js` as `MaskProcessedEnvs.cs` for `Config()` (masks `parsed`/`injected`/`preExisted` on every processed env AND the destination `processEnv` dict itself for every resolved key, not just what gets logged/returned) plus a simpler flat-dict mask for `Get()` matching its own simpler `parsed` shape.

    - Fixing `Get()`'s new `NormalizeDotenvConfigIgnore` call surfaced a SEPARATE latent bug in that helper itself: its ignore-merge path hand-reconstructed a plain `new ConfigOptions {...}` by listing fields manually, silently dropping any derived type's own fields (`GetOptions.All`/`.Format`) - real JS does a non-mutating `{ ...options, ignore: [...] }` full spread. 60. **Continuing the same static-audit pass as trap #59 (the OTHER never-cross-checked vendored pattern-matching dependency, `Interop.IgnoreJs/IgnoreRule.cs`) found multiple, more serious regex-construction bugs - confirmed live against the real `ignore` npm package, which turns out to be directly live-callable too (`@dotenvx/tooling`'s `ignore` export, the exact one `prebuild.js`/`precommit.js` use via `ignore().add(content).ignores(path)`).** Like `IndexJs.cs`, this was a from-scratch reimplementation based on reading the public `ignore` package's docs, never verified against what dotenvx's own vendored copy actually does. Four distinct bugs, all confirmed via a live-oracle test matrix (`node -e "require('@dotenvx/tooling').ignore().add(pattern).ignores(path)"`) before and after the fix:
    - **A basename (no-`/`) pattern didn't match nested content under a match** - `node_modules` failed to match `node_modules/foo` (the old regex had no trailing boundary after the literal pattern, so an exact end-of-string match was required - `$` directly after the pattern text).
    - **A directory-only (single trailing `/`) pattern WRONGLY matched the bare name itself** - `build/` incorrectly matched `build` (should only match `build/file`-style nested paths - confirmed live that `ignore().add('build/').ignores('build')` is `false`; the bare name is only "ignored" if the test path ITSELF carries a trailing slash, e.g. `ignores('build/')` is `true`).
    - **An anchored pattern (containing `/` anywhere except as a single trailing character) didn't match nested content under it either** - `/build` failed to match `build/file` (no equivalent-nested-content suffix on the anchored branch at all).
    - **`dir/**` matched the bare directory name**, when the trailing `/**` requires a literal, mandatory slash before the wildcard - `foo/**` wrongly matched bare `foo` (the old conversion made the slash optional, via the exact same `(?:/.*)?` shape already correctly used by `Interop.PicomatchJs`'s OWN `/**` handling - a reminder that these are two independent regex-building functions for two different matching specs, even though they look superficially similar; "fix one the same way as the other" would have been wrong here).
    Root-caused each one by building a comprehensive pattern/path test matrix against the live oracle FIRST (about 15 scenarios covering basename/anchored/directory-only/double-star/character-class/negation), deriving the correct regex-construction rule for each case, THEN rewriting `IgnoreRule.ConvertToRegex` once against the whole matrix rather than patching one symptom at a time. The general unifying rule that emerged: matching a pattern should ALSO match everything nested below the match point (`(?:\/.*)?$` suffix) in every case EXCEPT a directory-only trailing-slash pattern, which requires that nested slash to be literally present (`\/.*$`, no bare-name option) - and separately, whether a pattern is "anchored" (prefix `^`) or "basename, any depth" (prefix `(?:^|.*\/)`) is determined by whether it contains `/` anywhere except as a single trailing character, independent of the suffix rule. A pre-existing character-class ([a-z]) unescape step (`CharacterSetRegex`, copied from `IndexJs.cs`'s identical need) had to be added too - the old code never had one at all, meaning bracket patterns like `file[0-9].txt` would have matched nothing before this fix either (confirmed live that the real package DOES support them).
    Found one stale C# unit test locking in the directory-only bug as if it were correct (`IgnoreTest.Add_DirectoryPattern_ShouldIgnoreDirectory` asserted `ig.Ignores("node_modules").ShouldBeTrue()` for pattern `"node_modules/"`) - fixed to `ShouldBeFalse()`, confirmed against the live oracle first. Also fixed that test class's own stale `Reference source: dotenvx/tests/lib/ignore.test.js` doc comment (no such file exists at this pin - same stale-reference pattern as trap #55's sweep; `ignore` was never dotenvx's own code to begin with, it's a live-callable `@dotenvx/tooling` export).
    **Lesson, same shape as trap #59's**: two separate "looks like a faithful reimplementation of a well-known npm package" helpers in this codebase had both drifted from the ACTUAL semantics their real upstream dependency provides, in both cases because neither was ever checked against a live oracle - despite `@dotenvx/tooling`'s `ignore` export (like `@dotenvx/primitives`' `match`/`scan`) being trivially callable via `node -e` the entire time. When a reference source doc comment says "C# equivalent of Node.js package X" without naming a specific verified-against call, that claim is unverified by default - check whether the real package is actually installed and live-callable before trusting the reimplementation's own internal consistency as proof of correctness.

66. **JS vs .NET regex/string differences that bit the sweep**: JS `\s` includes U+FEFF, U+00A0 and the Unicode spaces (.NET ECMAScript-mode `\s` is ASCII-only); JS `trim` strips U+FEFF (.NET `Trim` does not); JS multiline `^`/`$`/`.` treat CR, LF, U+2028, U+2029 as terminators (.NET Multiline only knows LF) - so a lone CR is a line break and U+2028 inside an unquoted value is NOT a break for the value class but IS a comment terminator; `String.replace(str,str)` replaces the FIRST occurrence only and expands `$$ $& $backtick $'` (replacement `$&` re-inserting the match caused an infinite expand loop before `JsReplacement`); JS `split(null)` splits on the text "null"; JS `||` treats empty string as falsy.
67. **Expand operator semantics (primitives)**: `:-` gives `env[k] || default` (empty counts as unset); `-` gives `has(k) ? env[k] : default`; `:+` gives `env[k] ? alt : ""`; `+` gives `has(k) ? alt : ""`; no operator gives `env[k] || ""`. Locked by `ParseTest.TestExpandOperatorsTreatEmptyValuesLikePrimitives`.
68. **Real `remove`/`upsert`/`sealed`/`publickeys` algorithms (read from the minified source)**: `remove` is line-based (normalise CRLF/CR to LF, drop the matching `[export ]name=` / `name: ` line, and if its value opens a quote with no closing quote consume following lines until one closes; restore a trailing newline only if the result is non-empty, restore CRLF style, return the source untouched if nothing matched). `upsert` replaces EVERY occurrence of the key (each keeps its own quote style) by swapping a placeholder per occurrence for the new value, appending `KEY="value"` (with a leading newline if the source is non-empty and lacks a trailing one) when absent. `sealed` needs every value of every key encrypted except `DOTENV_PUBLIC_KEY*` and `*_PLAIN`. `publickeys` keeps the last value per `DOTENV_PUBLIC_KEY*` key in first-appearance order.
69. **Tool-layer mangling to remember when editing parser code**: Edit/Write and shell heredocs can rewrite backslash and `uXXXX` text (a heredoc turned a char literal of two backslashes into one). Use `(char)92`/`(char)0xA0` constants in C#, token substitution in test tables, and a node script from a quoted heredoc only when it contains no backslashes. Raw U+2028 in C# source is a line terminator - never type it literally.

73. **Full-parity port (2026-10-05): lessons from Armor, native stores, lock, secret managers, spinner and dynamic dispatch.** Found by comparing against the real Node CLI with fakes (`FakeSecretCli`, `FakeArmorServer`), never by reading the JS alone:

    - **`conf@10` (`.device-key`) salts pbkdf2 with `iv.toString()`** (UTF-8 decoded random bytes, replacement characters included); .NET reproduces it exactly (40 random IVs round-trip both ways in `ArmorStoreParityTest`). The session file is a plain `.env` written by `jsonToEnv` (values unescaped).
